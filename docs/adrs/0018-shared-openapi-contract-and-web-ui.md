# ADR 0018: Shared OpenAPI contract and a separately deployed web UI

Date: 2026-09-08

## Status

Accepted.

## Context

The server exposes a complete REST + SSE API ([server](../system-components/server.md)) and, since
[ADR 0016](0016-oauth2-resource-server-and-user-attribution.md), a login story for browser clients, but
there was no client: `AGENTS.md` declared the UI out of scope, and the architecture named three future
clients (web UI, VSCode extension, IntelliJ plugin) that would all have to re-describe the same endpoints
and DTOs. Hand-written client types drift silently from Kotlin DTOs, and three hand-written clients drift
three ways. The web UI is the first consumer and also needs a deployment story on the same Kubernetes
cluster as the server, without introducing a second origin and CORS configuration.

Constraints that shaped the decision:

- The controllers are the truth. Any contract has to be derived from them, and a change to a controller
  or DTO must not be mergeable without its contract update — inside the existing `./kotlin check`, without
  a new build plugin.
- The contract must serve non-JVM consumers (TypeScript today, IDE plugins later) and must describe the SSE
  stream (`GET /api/v1/agents/watch`) and RFC 9457 problem details, not only plain JSON responses.
- The browser must send `Authorization: Bearer` on every call including the SSE stream, so a native
  `EventSource` is out ([ADR 0016](0016-oauth2-resource-server-and-user-attribution.md)).
- No secret other than the user's own access token may reach the browser; repository tokens stay
  server-side (`hasToken` only, [ADR 0012](0012-server-managed-repository-credentials.md)).
- The Kotlin toolchain does not build JavaScript; the web build must stay a separate, fast pipeline.

## Decision

1. **The contract is generated by springdoc from the Spring controllers and committed as
   `api/openapi.yaml`.** The server serves it anonymously at `GET /v3/api-docs[.yaml]`
   (`SecurityConfiguration.ANONYMOUS_GET_PATHS`); Swagger UI is not shipped (only
   `springdoc-openapi-starter-webmvc-api`). `OpenApiConfiguration` in the `api` Modulith module contributes
   the `bearerAuth` JWT scheme applied to every operation, stable `operationId`s derived from the handler
   (`<resource><Method>`, e.g. `agentRunList`) and the shared `ProblemDetail` schema; controllers carry
   `@Tag`/`@Operation`/`@ApiResponse` for summaries and non-default status codes, the SSE endpoint documents
   `text/event-stream` frames as `AgentRunEvent`, `AgentRunResponse.spec` is a free-form object.
   `springdoc.paths-to-match=/api/**` keeps actuator and framework endpoints out;
   `writer-with-order-by-keys` makes the output deterministic.
2. **Drift is a failing test.** `OpenApiContractTest` (a `PostgresIntegrationTest` with MockMvc) fetches the
   live YAML, strips the request-dependent `servers:` block and compares it with the committed file; a
   mismatch fails `./kotlin check` with a unified diff. `SIFT_UPDATE_OPENAPI=true` rewrites the file instead
   (`api/README.md`).
3. **One framework-agnostic TypeScript client, generated from the committed spec.** `web/packages/api-client`
   (`@sift/api-client`) holds `openapi-typescript` output (`schema.d.ts`, committed and guarded by
   `pnpm generate:check`), a typed `openapi-fetch` client with bearer middleware and `SiftApiError`
   (`ProblemDetail`) mapping, and `watchAgentRuns`, a `fetch`/`ReadableStream` SSE parser that sends the
   bearer token, honours `id:`/`event:`/multi-line `data:`/comment frames and reconnects with
   `Last-Event-ID` and a fresh token. The package has no React dependency so the VSCode/IntelliJ work can
   reuse it unchanged.
4. **The web UI is a React SPA in the same pnpm workspace** (`web/apps/web`: React 19 + Vite + TypeScript,
   Tailwind v4 + shadcn/ui, TanStack Router + Query, `oidc-client-ts` PKCE against the provider announced
   by `GET /api/v1/auth/config`). It owns all React-specific code (query hooks, routes, screens) on top of
   `@sift/api-client`; screens follow one layering (`api/hooks` → `features/<resource>` → route) so the
   plugins can copy them.
5. **`sift-web` is a separate nginx image that also proxies the API** (`web/apps/web/Dockerfile`,
   `nginx.conf`): nginx serves the SPA with history fallback and forwards `/api/` and `/v3/api-docs` to the
   `sift-server` Service unbuffered with a one-hour read timeout, so REST and SSE stay same-origin and the
   server needs no CORS configuration. The upstream is a runtime-resolved `SIFT_SERVER_UPSTREAM`; the
   container runs read-only as the image's `nginx` user with a single `/tmp` volume. Manifests live in
   `k8s/manifests/web/` next to the server's; no Ingress is shipped (a commented example documents the SSE
   buffering/timeout annotations). Locally the Vite dev server plays the proxy role.
6. **The web workspace is checked by pnpm, not by the Kotlin toolchain.** `./kotlin check` guards the
   contract; `pnpm check` in `web/` (`generate:check`, lint, format, typecheck, Vitest + Testing Library +
   MSW, `vite build`) guards the client. Browser end-to-end tests (Playwright) are not part of this
   decision.

## Consequences

- One source of truth: a DTO change shows up as a red `OpenApiContractTest`, is regenerated with one
  command, and `pnpm typecheck` then points at every client site that has to adapt. The spec and the
  generated types are reviewed as ordinary diffs.
- `GET /v3/api-docs` is public information about the API surface, not about data; it adds no data exposure
  but does reveal endpoint names to anonymous callers — accepted, the contract is meant to be shared.
- Two deployable units (`sift-server`, `sift-web`) instead of one. The trade-off buys independent release
  cadence, a static-only web image with no JVM, and no CORS; the cost is that the proxy must be kept
  SSE-safe (`proxy_buffering off`, long timeouts) at nginx *and* at any Ingress in front of it.
- The SPA holds the user's access token in memory/session storage (public client, silent renew); an open
  SSE stream is not cut when the token expires (server behaviour from ADR 0016) and the client reconnects
  with a fresh token.
- The IDE plugins get a ready input (`api/openapi.yaml`, `@sift/api-client`) but are not built here;
  publishing the client as a package is a follow-up when the first plugin needs it.
- springdoc tracks Spring Boot 4/Jackson 3; a springdoc upgrade can change the rendered YAML and must be
  regenerated (the drift test makes such upgrades visible rather than silent).
- No CI job runs `pnpm check` yet; `AGENTS.md` names it as part of the Definition of Done for web changes.
